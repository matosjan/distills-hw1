# Оптимизация инференса Qwen2.5-7B-Instruct для оценки траекторий LLM-агента

## 1. Выбор модели и контекста применения

Для работы выбрана **[Qwen2.5-7B-Instruct](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct)**. Она используется как **LLM-as-judge**: получает исходную задачу, действия агента и результаты вызовов инструментов, затем выставляет оценку с кратким обоснованием.

Рассматриваем офлайн-инференс по сохранённым траекториям. Для анализа примем пакет из **1 000 траекторий**, вход до **8 192 токенов** и ответ до **256 токенов**.

Под judge выделена самая слабая из доступных GPU. Цель оптимизации — сократить время обработки пакета и потребление памяти.

## 2. Целевая аппаратная платформа

Используем **[NVIDIA T4](https://www.nvidia.com/en-us/data-center/tesla-t4/)** с **16 ГБ памяти** и скоростью обмена данными с памятью около **320 ГБ/с**.

Веса модели в FP16 занимают примерно **15 ГБ**. Для контекста и рабочих данных остаётся мало места. Это ограничивает длину траекторий и количество примеров, которые можно оценивать одновременно.

## 3. Архитектура модели

Qwen2.5-7B-Instruct — трансформер, который генерирует ответ авторегрессионно по одному токену. Входные токены превращаются в векторы из **3 584 чисел** и проходят через **28 блоков**. [Конфигурация модели](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct/blob/main/config.json).

В каждом блоке есть две основные части:

- **Attention** связывает текущий токен с доступным контекстом.
- **FFN** — полносвязная сеть, которая обрабатывает представление каждого токена.

После последнего блока модель вычисляет вероятности следующего токена. В attention используется **GQA**: несколько голов разделяют общие ключи и значения, что уменьшает размер KV-cache.

Основные вычисления — матричные умножения в attention и FFN. Память занимают веса, рабочие данные и KV-cache, который растёт по мере обработки входа и генерации ответа.

## 4. Вычислительные затраты и узкие места

В нашем сценарии ожидаем три узких места:

- **Обработка длинной траектории.** Для каждого входного токена выполняются вычисления в attention и FFN. Чем длиннее траектория, тем больше работы.
- **Генерация оценки.** Ответ строится по одному токену. При небольшом батче прочитанные веса используются для меньшего количества примеров, поэтому скорость памяти может ограничивать генерацию. [Описание этапов инференса](https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/).
- **Нехватка памяти.** Веса в FP16 занимают почти всю память T4. KV-cache и рабочие данные дополнительно ограничивают размер батча.

Это предполагаемые узкие места; их точный вклад нужно проверить замерами.

## 5. Системные ограничения

- **Память:** веса модели, KV-cache и рабочие данные должны помещаться в 16 ГБ. Это главное ограничение на число одновременно оцениваемых траекторий.
- **Объём данных:** вход — до 8 192 токенов на траекторию, ответ — до 256 токенов.
- **Время обработки:** основной показатель — время оценки всего пакета из 1 000 траекторий. Строгий срок для отдельной оценки не задан.

## 6. Гипотезы по ускорению

Предлагаем проверить следующие способы:

- **[Квантизация весов](https://huggingface.co/docs/transformers/en/quantization/overview).** Хранить веса в 8 или 4 битах, чтобы освободить память для контекста и большего батча. Ускорение зависит от реализации и её поддержки на T4.
- **[Обработка батчами](https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/).** Оценивать несколько траекторий вместе, объединяя примеры похожей длины. Это поможет эффективнее использовать GPU, пока батч помещается в память.
- **[Повторное использование KV-cache](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/).** Сохранять результаты обработки одинакового начала запросов, например инструкции judge. Выигрыш будет заметнее при длинном общем начале; уникальные части траекторий всё равно придётся обработать.
- **[Квантизация KV-cache](https://huggingface.co/docs/transformers/en/kv_cache#quantized-cache).** Уменьшить память под контекст, если именно кеш мешает увеличить батч. Дополнительные преобразования могут замедлить работу.
- **[Спекулятивное декодирование](https://arxiv.org/abs/2211.17192).** Маленькая модель предлагает токены, основная проверяет их одним форвардом. Метод полезен, если предложения часто принимаются. Для наших коротких ответов общий выигрыш может быть небольшим, а дополнительной модели потребуется память.

## 7. Инженерные компромиссы

| Метод | Что выигрываем | Чем платим |
|---|---|---|
| Квантизация весов | Освобождаем память | Оценки judge могут измениться; нужна совместимая с T4 реализация |
| Батчи | Быстрее обрабатываем пакет | Требуется больше памяти |
| Повторное использование KV-cache | Экономим вычисления для общего начала запросов | Хранение кеша занимает память и усложняет систему |
| Квантизация KV-cache | Уменьшаем память под контекст | Возможны изменения оценок и дополнительные затраты на преобразования |
| Спекулятивное декодирование | Можем ускорить генерацию без потери качества при точном алгоритме | Дополнительная модель занимает память и усложняет поддержку |

После квантизации нужно проверить, насколько изменились оценки на одном и том же наборе траекторий, желательно с эталонными оценками.
